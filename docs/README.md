# Reverse-Proxy WAF

Webアプリの手前に置く**リバースプロキシ型の WAF(Web Application Firewall)**です。
クライアントからのリクエストを検査し、XSS・SQLインジェクション・パストラバーサル・コマンドインジェクションなどの攻撃を**バックエンドに届く前に遮断**します。バックエンドのアプリには手を加えず、別プロセスとして起動します。

`python3 waf.py` 一つで、WAF(既定 :8080)と、攻撃マップ付きの管理ダッシュボード(既定 :8090)が同時に起動します。依存は Python 標準ライブラリのみです。

```
ブラウザ ──► [ WAF :8080 ] ──検査──► バックエンドのアプリ
                 │   └─► waf.log ──► [ ダッシュボード :8090 ](同一プロセス・攻撃マップ)
                 ├─ 危険 → 403 で遮断(blockモード)/ ログのみ(detectモード)
                 └─ 応答に CSP 等のセキュリティヘッダを付与
```

## 主な機能

- **リクエスト検査**: URL・クエリ・ヘッダ・ボディ・Cookie を多段デコードして検査(15カテゴリ・87ルール)。ルールごとに「遮断 / 検知のみ / 使わない」を選べます。
- **応答の検査**: バックエンドが返す HTML 内の攻撃スクリプト(Stored XSS)を無害化・遮断・記録します。
- **DoS・不正接続対策**: レート制限、同時接続上限、Slowloris / Slow POST 対策、ボディ上限、リクエストスマグリング対策、攻撃の繰り返しによる自動BAN。
- **IP・国の制御**: 手動BAN、IP許可リスト、除外IP、国の許可 / ブロック(オフラインGeoIP対応)。
- **複数バックエンドの同時防御**: 専用ポート・ホスト名・パスで振り分け。バックエンドごとにモード、ルール、IP制御、稼働状態を管理。
- **管理ダッシュボード**: ホーム、トラフィック、リアルタイム/集計の攻撃マップ、イベントログ(Burp風の詳細表示)、状態ログ、IP管理、ルール管理、設定。ライト / ダークテーマ対応。
- **攻撃アラート**: 攻撃を検知すると、警報バナーと六角形の「EMERGENCY」背景で知らせます。
- **ユーザー・組織・権限**: 管理者 / アナリスト / 一般の3役割、組織の木と担当範囲、ログのマスク、申請(チケット)の流れ。
- **ログの保存と書き出し**: 組織ごとの保存期間、書き出し、期限切れ削除。
- **外部連携**: Webhook 通知、申請のメール通知、逆プロキシ(nginx 等)の背後での運用。

> 教育・許可された検証環境専用です。公開サーバーや許可のないシステムでは使用しないでください。

## フォルダ構成

一番上には、起動用の2つだけを置いています。ほかは役割ごとのフォルダに分けています。

```
waf_new/
├─ waf.py                  本体。ダブルクリックで WAF とダッシュボードを起動
├─ start_rules_tool.bat    追加ルールの管理ツールを起動(ブラウザが開きます)
├─ src/                    プログラムの部品と同梱データ
├─ config/                 設定(waf_config.json・custom_rules.json)
├─ data/                   実行時に増えるデータ(ログ・申請・操作記録・証明書など)
├─ tests/                  動作確認テスト
└─ docs/                   このREADME
```

| 場所 | 中身 |
|---|---|
| `waf.py` | **本体**(リバースプロキシ + ダッシュボードを同時起動。待受・転送・遮断・ヘッダ・レート制限・ログ) |
| `src/waf_rules.py` | 署名ルールと多段デコード(XSS / SQLi / traversal / cmdi ほか) |
| `src/waf_backend.py` | バックエンドごとの設定(ルールプリセット・上書き・パス別ルール・防御モード) |
| `src/waf_extras.py` | 追加の防御(自動BAN・低速接続対策・IP/国制御・Webhook など)、個人のアラート設定 |
| `src/waf_org.py` | 組織の木・役割・担当範囲・ログのマスク |
| `src/waf_tickets.py` | 申請(チケット)と通知 |
| `src/waf_logstore.py` | ログの保存場所・保存期間・書き出し |
| `src/waf_crypt.py` | ログ詳細の暗号化(組織ごとの公開鍵・復号の操作記録・鍵作成・オフライン復号) |
| `src/waf_custom.py` / `src/waf_rules_tool.py` | 追加ルールの管理(再起動不要)/ ルール管理ツール(`start_rules_tool.bat` から起動) |
| `src/waf_countries.py` | 国コード・国名(日本語/英語)の一覧 |
| `src/dashboard.py` | ダッシュボード + 攻撃マップ(`waf.py` が取り込み起動。単体実行も可) |
| `src/world_land.svg` | ダッシュボード同梱の世界地図データ(CDN不要) |
| `config/waf_config.json` | 設定(待受ポート・モード・ルール・ダッシュボード 等)。無ければ既定値で起動し、画面で変更すると作られます |
| `config/custom_rules.json` | 追加ルール(ルール管理ツールで編集) |
| `data/logs/` | 検知ログ(WEB別・日次)。`data/waf.log` は従来形式 |
| `data/tickets.json` ほか | 申請・操作記録(`enc_audit.jsonl`)・各種履歴(`*_history.jsonl`)・`geo_cache.json`・`waf_cert.pem` / `waf_key.pem`(自己署名証明書。無ければ自動生成)・`log_exports/`(組織の書き出し) |
| `tests/test_waf.py` / `tests/test_merged.py` | 動作確認テスト(アプリ不要、ダミーバックエンドで検証) |

設定ファイルの中でファイル名だけを書いたもの(例: `"tickets_file": "tickets.json"`)は、`data/` の中に作られます。`config/` または `data/` から書き始めると、`waf.py` のあるフォルダからの場所になります。絶対パスもそのまま使えます。

依存は **Python 標準ライブラリのみ**。追加インストールは不要です(オフラインGeoIPを使う場合のみ任意で `python-geoip-geolite2`)。

## 使い方

### 1. バックエンド(掲示板アプリ)を起動

> **このリポジトリにバックエンドのアプリは含まれていません。** 以下の `stored-xss-poc/app.py` は、作者が動作確認に使った Stored XSS のデモ用掲示板で、付属していません。転送先のアプリ(5000 番など)は各自で用意してください。手軽に試すだけなら `python3 -m http.server 5000` と `python3 waf.py --backend http://127.0.0.1:5000 --no-listen-tls` で動きます(トップの README を参照)。

```bash
cd stored-xss-poc
python3 app.py          # https://127.0.0.1:5000 で起動
```

### 2. WAF を起動(別ターミナル)

```bash
cd waf
python3 waf.py          # WAF(:8080)とダッシュボード(:8090)を同時に起動
```

> **WAF とダッシュボードは1プロセスで動きます。**`python3 waf.py` だけで、
> WAF(既定 `https://0.0.0.0:8080`)と攻撃マップ付きダッシュボード
> (既定 `http://127.0.0.1:8090`)の両方が起動します。別途 `dashboard.py` を
> 起動する必要はありません(単体起動も可能・下記)。

### 3. アクセス先を 5000 → **8080** に変える

これまで `https://127.0.0.1:5000/login` に直接アクセスしていたところを、
**WAF のポート `https://127.0.0.1:8080/login`** に変更します。
WAF が検査したうえでバックエンド(5000)へ転送します。

> **アクセスは必ず `127.0.0.1`(または `localhost`)で。** `0.0.0.0` は「待受用」の
> アドレスでブラウザからは開けません(`ERR_ADDRESS_INVALID` になります)。
>
> 既定で WAF は **HTTPS(8080)で待受け**ます。証明書(`waf_cert.pem` /
> `waf_key.pem`)が無ければ初回起動時に自己署名証明書を自動生成します。
> 自己署名なのでブラウザは警告を出します(「詳細設定 → アクセスする」で続行)。
> HTTP で待受けたい場合は `waf_config.json` の `"listen_tls": false` にして
> `http://127.0.0.1:8080` でアクセスしてください。

### コマンドライン引数

設定は `waf_config.json` で行いますが、起動時の引数で一部を上書きできます(指定した項目だけ上書き。`--save-config` で保存)。一覧は `python3 waf.py --help`。

```bash
python3 waf.py                                                   # waf_config.json で起動
python3 waf.py --backend http://127.0.0.1:3000 --no-listen-tls   # 任意のページの前段に
python3 waf.py --path-route /shop=https://192.168.200.88:5000 --path-route /blog=http://192.168.200.90:3000
python3 waf.py --site shop=8081=https://192.168.200.88:5000 --site blog=8082=http://192.168.200.90:3000
python3 waf.py --allow-country JP --block-ip 203.0.113.0/24 --response-xss block --webhook http://127.0.0.1:9000/waf-events
```

Windows では `waf.py` をダブルクリックでも起動できます。

## プライベートネットワーク(LAN)に出す

WAF を同一 LAN の他の端末からアクセスできるようにします。WAF は既定で
`0.0.0.0:8080` を待ち受けるので、**設定変更なしで LAN に出ています**。あとは
「正しいアドレス・証明書・ファイアウォール」の3点だけ確認します。

### 1. アクセスする URL

WAF を起動すると、バナーに LAN 用の URL が表示されます。

```
  アクセス   : https://127.0.0.1:8080       ← この端末から
  LAN から   : https://192.168.x.x:8080     ← 同一ネットワークの他端末から
```

他の端末のブラウザで `https://<この端末のLAN IP>:8080/login` を開きます
(LAN IP は上記バナー、または `ipconfig`(Windows)で確認)。
**経路は「LAN端末 → WAF(LAN IP)→ アプリ(loopback 5000)」**。アプリには WAF が
ループバックで中継するため、アプリ側を LAN に晒す必要はありません。

### 2. 証明書(自己署名)

WAF は起動時に、この端末の **LAN IP とホスト名を SAN に含めた**自己署名証明書を
自動生成します(ネットワークが変わって LAN IP が変化した場合は自動で再生成)。
自己署名のため、各端末のブラウザで初回に警告が出ます →「詳細設定 → アクセスする」
で続行してください。警告を避けたい場合は `"listen_tls": false` で HTTP 運用も可能です。

### 3. Windows ファイアウォールで受信を許可

他端末から開けないときは、Windows の受信規則でポートを開けます(管理者 PowerShell):

```powershell
New-NetFirewallRule -DisplayName "WAF 8080" -Direction Inbound -Action Allow -Protocol TCP -LocalPort 8080
# ダッシュボードも LAN に出す場合のみ(下記参照)
New-NetFirewallRule -DisplayName "WAF Dashboard 8090" -Direction Inbound -Action Allow -Protocol TCP -LocalPort 8090
```

削除するときは `Remove-NetFirewallRule -DisplayName "WAF 8080"`。

### ダッシュボードの公開範囲

既定で **ダッシュボードも LAN に公開(`dashboard.host: "0.0.0.0"`, ポート 8090)** します。
WAF 起動時のバナーにダッシュボードの LAN URL も表示されます。他端末から開けない場合は
**受信 TCP 8090 もファイアウォールで許可**してください(上の PowerShell 例に 8090 を含めています)。

> ダッシュボードには**設定変更やIPブロックの操作・攻撃統計**が含まれ、認証はありません。
> LAN 公開する場合は信頼できる検証ネットワーク内に限定してください。この端末のみに戻すには
> `dashboard.host` を `"127.0.0.1"` にします。

> 注意: これはあくまで**プライベートネットワーク内**での利用を想定しています。
> 元の PoC と同様、インターネットに直接公開しないでください。

## モード切替(block / detect)

`waf_config.json` の `"mode"` で切り替えます。起動時に `--mode` でも上書き可能です。

| モード | 挙動 | 用途 |
|---|---|---|
| `block` | 危険なリクエストを **403 で遮断** | 本番の防御(既定) |
| `detect` | 遮断せず **ログに記録して素通し** | 導入初期の誤検知チェック・監視 |

```bash
python3 waf.py --mode detect     # まず監視モードで誤検知を確認
python3 waf.py --mode block      # 問題なければ遮断モードへ
```

導入手順の推奨: **まず `detect` でしばらく運用 → `waf.log` に正当なリクエストが
誤検知されていないか確認 → `block` に切替**。

## 防御の内容

### 検査する場所(`inspect`)
URL パス / クエリ文字列 / フォーム本体 / JSON 本体(再帰的)/ 主要ヘッダ
(User-Agent, Referer, X-Forwarded-For)。Cookie は誤検知が多いため既定 OFF。

### 難読化対策
マッチ前に **URL デコード(多重)→ HTML エンティティデコード → Unicode正規化(NFKC)
→ 制御文字除去** を行い、`%253Cscript%253E` や `&lt;script&gt;`、全角などの
難読化を剥がしてから判定します。

### 検知ルール(15カテゴリ・計87ルール)

`waf_config.json` の `rules` でカテゴリ単位 ON/OFF、`disabled_rules` でルールID単位の無効化。
ダッシュボードの⚙設定 →「ルール単位の詳細設定を開く…」から**ルール1件ずつ**切替できます。

| カテゴリ | 代表的な検知 |
|---|---|
| `xss` | `<script>`, `on...=`, `javascript:`, `<svg/iframe/img onerror>`, `document.cookie`, テンプレート式 ほか(22) |
| `sqli` | `UNION SELECT`, `OR 1=1`, SQLコメント, 時間ベース, `information_schema`, エラーベース ほか(12) |
| `traversal` | `../`, `%2e%2e`, `/etc/passwd`, `php://`, NULLバイト ほか(6) |
| `cmdi` | コマンド連結, `$(...)`, バッククォート, `wget|sh`, Windowsコマンド ほか(6) |
| `ssrf` | クラウドメタデータ(169.254.169.254), 内部ホスト/プライベートIP, `gopher/dict/file://` ほか(5) |
| `xxe` | `<!DOCTYPE/<!ENTITY`, 外部エンティティ `SYSTEM`, `file://`参照 ほか(4) |
| `ssti` | `${...}`, `{{7*7}}`, `<%= %>`, `__class__/__globals__` ほか(5) |
| `nosqli` | Mongo演算子 `$where/$ne/$gt`, 配列演算子注入 ほか(3) |
| `ldap` | LDAPフィルタ注入 `*)(|(` ほか(2) |
| `crlf` | `%0d%0a`, HTTPレスポンス分割, ヘッダ注入(3) |
| `redirect` | オープンリダイレクト `//evil`, `@` 回避(2) |
| `upload` | 危険拡張子, 多重拡張子, Webshell痕跡(3) |
| `scanner` | sqlmap/nikto/nmap 等のUA, `.env/.git/wp-admin` 等の探索(3) |
| `deser` | Java `rO0AB`, PHP `O:/a:`, Python pickle(3) |
| `protocol` | **Log4Shell** `${jndi:}`, Spring4Shell, プロトタイプ汚染, GraphQL ほか(8) |

> 既定はすべて ON。誤検知が出るルールだけ個別に OFF にできます。

### セキュリティレスポンスヘッダ(`security_headers`)
バックエンドの応答に以下を付与(多層防御)。仮に検査をすり抜けても
ブラウザ側で実行を抑止します。

- `Content-Security-Policy: default-src 'self'; script-src 'self'; ...`
  (インラインスクリプトを禁止 → stored XSS の実行を無効化)
- `X-Frame-Options: DENY` / `X-Content-Type-Options: nosniff`
- `Referrer-Policy: no-referrer` / `Permissions-Policy`(geolocation 等を禁止)

> 注: 厳格な CSP はアプリ内のインライン `<script>` も止めるため、デモアプリの
> 一部挙動が変わることがあります。挙動確認が目的のときは `security_headers.enabled`
> を `false` にするか、CSP を緩めてください。

### レート制限 / DDoS対策(`rate_limit`)
多層のレート制御を備えます(すべてダッシュボードの⚙設定から変更可):

- `action: "drop"`(既定)… 上限超過で**応答を返さず接続を切断**。`"429"` なら 429 応答。
- **バースト上限** `burst_max`/`burst_seconds`(既定 30req/3s)… 短時間に集中した
  リクエストを検知したら**即BAN**。緩やかな通常上限より早くフラッドを止めます。
- **自動BAN** `ban_threshold`/`ban_seconds`(既定 5回/300秒)… 繰り返し違反した接続元を
  一定時間 全drop。
- **BANエスカレーション** `ban_escalate`(既定ON)… 再犯するほどBAN時間を自動的に倍々で延長。
- **接続頻度BAN** `conn_burst_max`/`conn_burst_seconds`(既定 60接続/5秒、0=無効)… HTTPを
  1本も送らない「TCP接続だけ」「TLSハンドシェイクだけ」のフラッドを、**接続の回数**で検知して
  即BAN。BAN中のIPはTLS握手の**前**(受付直後)に切るので、暗号計算のCPUを使いません。
- **TLS握手タイムアウト** `tls_handshake_timeout_seconds`(既定 5秒)… TLS握手はワーカー
  スレッド側で行い、時間内に終わらない接続は切断します。握手を始めない1本の接続のせいで
  WAF全体が止まる(HTTPS待受けの旧挙動)ことはありません。
- **全体レート上限** `global_max_rps`(既定0=無効)… 全IP合計が毎秒この数を超えたら
  超過分を drop(ロードシェディング。大規模分散攻撃時のサービス保護)。
- **手動ブロックリスト** `blocklist` … 指定 IP / CIDR を常に drop(ダッシュボードから操作)。

レート制限・BANは**実際の接続元IPごと**に判定します。

#### ログ件数(カウント)の意味と「接続の流れ」パネル
`waf.log` に残る/数えられるのは **HTTPリクエストとして処理できたもの** と、
**受付直後にゲートで切った接続(RATELIMIT/ban 等。1接続=1件、1秒ごとに集約)** だけです。
接続だけ・ゴミ送信・TLS握手の失敗・無言のまま切れた接続は `waf.log` には残りません。
そのため、**同じDoSでも「WAFが接続を拒否できた速さ」で件数が変わります**(速く切るほど
攻撃側が再接続を速く繰り返し、件数が増える。他のWAFと件数を比べても攻撃量の比較にはなりません)。
実際の接続の流れは、ダッシュボード **🚫IP管理 →「接続の流れ」** と、コンソールの
`[接続/30秒] ...` 行で確認できます(受理/ゲート遮断の内訳/TLS握手の成功・失敗/リクエスト無し/不正HTTP/処理件数。WAF起動後の累計)。

## 追加の防御

次の機能は、ダッシュボードの **⚙設定 →「追加の防御」** と **🚫IP管理** から変更でき、即時反映されます。

| 機能 | 内容 | 設定キー / 操作 |
|---|---|---|
| 応答の Stored XSS 検査 | バックエンドが返す HTML 内の攻撃スクリプト(`<script>alert…`、自動発火 `onerror=` の外部送信、`javascript:` URL、危険な `srcdoc` 等)を **無害化 / 403遮断 / 記録のみ**。正規のスクリプトや `onclick` は残す。gzip 応答も展開して処理 | `response_inspection.action` = `sanitize`/`block`/`monitor`/`off`、ルール `RESP-001〜004` |
| 攻撃の繰り返しで自動BAN | 検知(BLOCK/DETECT)を窓内にN回出した送信元をBAN。detect モードでは BAN せず「BAN相当」を記録 | `autoban.enabled/threshold/window_seconds/ban_seconds` |
| Slowloris / Slow POST 対策 | 1バイト目から `header_timeout_seconds` 以内にヘッダが揃わない、`body_timeout_seconds` 以内にボディが届かない接続を切断。繰り返す送信元はBAN | `header_timeout_seconds`、`body_timeout_seconds`、`slow_ban.*` |

## ログの見方(`waf.log`, JSON Lines)

1 行 1 イベント。`action` は `PASS`(通過)/ `BLOCK`(遮断)/ `DETECT`(検知のみ)/
`RATELIMIT`(レート制限)/ `ERROR`。通常の閲覧も `PASS` として記録されるので、
「ログが全く出ない」ときはまず WAF に到達できているか(`127.0.0.1:8080` で開けているか)
を確認してください。`access_log` を `false` にすると `PASS` は記録しません。

```json
{"action":"BLOCK","client_ip":"203.0.113.45","ip_src":"egress","method":"POST","path":"/board",
 "hits":[{"id":"XSS-001","category":"xss","severity":"critical",
          "description":"<script> タグ","matched":"<script","field":"form:body"}],
 "ts":"2026-10-14T12:34:56"}
```

`field` でどこに攻撃があったか(`form:body` = 投稿本文)が分かります。

### 送信元IPは必ずグローバルIPで記録(`log_global_ip`)

ログの `client_ip` は **必ずグローバルIP** に解決して記録します(既定 ON)。ローカル
IPのままでは意味がないためです。`ip_src` フィールドに解決の由来が入ります。

| `ip_src` | 意味 |
|---|---|
| `remote` | 接続元がそのままグローバルIP(インターネット経由の直アクセス) |
| `reported` | LAN内の端末の**ブラウザが申告した公開IP**(VPN出口など)。下記「クライアント申告方式」 |
| `xff` | 信頼する `X-Forwarded-For` 内のグローバルIPを採用(下記 `trust_xforwarded_for`) |
| `egress` | 接続元が内部/ローカルIPで、申告も無い → **WAFホストの出口グローバルIP**(`ipinfo.io` 等)で代用 |
| `local` | グローバルIPを取得できなかった場合のみ接続元を記録(オフライン時のみ) |

判定の優先順位は `remote` → `xff` → **`reported`** → `egress` → `local` です
(`reported` は接続元がプライベート/ループバックIPのときだけ採用します)。

- 出口グローバルIPは起動時に先読み(`ipinfo.io/ip` →`api.ipify.org`→`ifconfig.me`)。
- **VPN の ON/OFF に追従します**: `self_ip_ttl` 秒(既定 60)ごとに出口IPを取り直し、
  変化があれば自動反映します(取得はバックグラウンドで行い、リクエスト処理は止めません)。
  VPN を切り替えたら最大60秒で新しいIPになります。すぐ反映したい場合は `self_ip_ttl`
  を小さくするか、WAF を再起動してください(古い値が残る場合は `data/geo_cache.json` を削除)。
- **レート制限は実際の接続元ごと**に判定するため、LAN内の端末識別には影響しません
  (ログ表示用IPのみグローバル化)。
- `trust_xforwarded_for` は **信頼できるプロキシ/ロードバランサの背後に置く場合のみ**
  `true` にしてください(XFF はクライアントが偽装可能なため、直公開時は `false`)。
- どうしても接続元(ローカルIP)をそのまま記録したい場合は `log_global_ip` を
  `false` にします。

### クライアント申告方式(LAN内の端末の公開IPを取得する)

**問題**: LAN内の端末が VPN を使っても、WAF に届く通信の送信元は端末のプライベートIP
(`192.168.x.x`)のままです(LAN宛の通信は VPN を通らないため)。端末が外へ出るときの
公開IPは、WAF からは見えません。従来の `egress` は「WAFホスト自身の出口IP」で代用して
いるだけなので、友人が VPN を使っても反映されませんでした。

**仕組み**: WAF が配る小さなスクリプト(`/__waf/cip.js`)が**ブラウザの中で**外部API
(`api.ipify.org` → `ipinfo.io/ip` → `ifconfig.me/ip` の順に試行)を呼び、その端末が実際に外へ出る
公開IP(VPN 経由ならVPNの出口IP)を取得して Cookie(`waf_cip`)に入れます。以降の
リクエストでは WAF がその Cookie を読み、ログ・ダッシュボード・攻撃マップの
「送信元グローバルIP」に使います(`ip_src: "reported"`)。実際の接続元プライベートIPは
従来どおり `conn_ip` に残ります。

```
LAN端末のブラウザ ─(1) HTMLを取得 ─► WAF ─► アプリ   ※WAFが <script src="/__waf/cip.js"> を差し込む
LAN端末のブラウザ ─(2) /__waf/cip.js を取得 ◄─ WAF
LAN端末のブラウザ ─(3) 外部API(VPN経由)で自分の公開IPを取得 → Cookie waf_cip に保存
LAN端末のブラウザ ─(4) 以降のリクエスト(Cookie付き) ─► WAF が waf_cip を読んで client_ip に採用
```

- **自動で有効**: `waf_config.json` の `client_ip_report.enabled` が `true`(既定)なら、
  HTML 応答にスクリプトが自動で差し込まれます(`inject_script`)。アプリ側の変更は不要です。
  WAF は差し込みのためバックエンドへ `Accept-Encoding: identity` で問い合わせます。
- **VPN の切替に追従**: ブラウザは次のタイミングで公開IPを取り直し、Cookie を更新します。
  - ページを開く(再読み込みを含む)たびに**必ず**
  - ページを開いている間は `ttl_seconds`(既定 45 秒)ごと
  - タブに戻ったとき・ウィンドウにフォーカスしたとき・戻る/進むで復帰したとき
  - ネットワーク変化(`online` / `navigator.connection` の変化)

  VPN を切り替えたら、**ページを再読み込みすれば約1秒で反映**されます(再読み込みしない場合は
  最大 `ttl_seconds` 秒)。再読み込みの**最初の1リクエスト(HTML本体)だけは切替前のIP**で記録され、
  その直後のリクエスト(CSS・画像・次の操作)から新しいIPになります。
  Cookie 自体は `cookie_seconds`(既定 3600 秒)保持するので、期限切れで WAF ホストの出口IP
  (`egress`)に戻って見えることはありません。
  ※ iPhone などはバックグラウンドのタブのタイマーが止まります。切替後はタブを開き直す/更新してください。
- **反映されないケース**: ① ブラウザ以外(curl 等)のアクセス、② 最初の1リクエスト(ページを
  開いた直後。申告前なので `egress` になります)、③ 広告ブロッカー等で外部APIが遮断される
  場合、④ Cookie を無効にしている場合。これらは従来どおり `egress` で記録されます。
- **CSP**: スクリプトが外部APIへ接続できるよう、WAF が付ける CSP の `connect-src` にだけ
  プロバイダのオリジンを追加します(`script-src 'self'` など他の制限は変わりません)。
- **ヘッダ申告**: Cookie の代わりに `X-Client-IP` ヘッダでも申告できます(API クライアント向け)。

> **セキュリティ上の注意(重要)**: 申告値は端末が自由に書き換えられます。そのため
> - **インターネット側(公開IP)からの接続の申告は無視**します(`private_only: true`)。
>   LAN内の端末だけが申告を使えます。
> - **レート制限・BAN・同時接続の判定は常に実接続IP(`conn_ip`)**で行います。申告を偽装しても
>   制限は回避できません。
> - 手動ブロックリストは、画面に出ているIP・信頼IP・実接続IPのどれが一致しても drop します。
>
> つまり `reported` は「LAN内の端末が自称した公開IP」であり、証拠ではなく**表示・地図用の参考情報**です。
> 国別ブロックも、LAN内の端末については自称IPの国で判定される点に注意してください。

無効にするときは `client_ip_report.enabled` を `false` にしてください(スクリプトの差し込み・
`/__waf/cip.js` の配信・申告の読み取りがすべて止まり、従来の `egress` 動作に戻ります)。

### リクエストの中身をダッシュボードで見る

ダッシュボードの「最近のイベント」の**行をクリック**すると、そのリクエストの詳細が
開きます。表示内容:

- 時刻 / アクション / 送信元IP(+由来)/ メソッド / パス / クエリ / ステータス
- **検知ルール**(ルールID・カテゴリ・深刻度・一致箇所 `field` と一致文字列 `matched`)
- **リクエストヘッダ**(User-Agent, Referer, Content-Type 等。Cookie は値をマスク)
- **リクエストボディ**(POST の中身。検知/遮断時のみ記録)

> **通過(PASS)したリクエストも GET/POST のボディまで記録**します(`log_pass_body: true`)。
> Cookie はキー名のみ表示し値は `***` にマスクします。
>
> **注意**: PASS のボディにはログイン等の資格情報(パスワード等)が含まれ得ます。
> 記録したくない場合は `log_pass_body` を `false` に(検知/遮断時のみボディ記録に戻ります)。
> ボディ・ヘッダを一切記録しない場合は `log_request_detail` を `false` に。

### HTTPS で待受ける

```json
"listen_tls": true,
"tls_certfile": "cert.pem",
"tls_keyfile": "key.pem"
```

これで `https://<ホスト>:8080/` でアクセスできます。

## ダッシュボード / 攻撃マップ

`waf.log` を可視化する監視画面です。**`python3 waf.py` で WAF と同時に起動**し、
既定で `http://127.0.0.1:8090` に表示されます(別途起動は不要)。

```
http://127.0.0.1:8090        ← WAF 起動時のバナーにも表示されます
```

- 約4秒ごとに自動更新されます。
- 画面内容: **脅威レベル**(LOW/MEDIUM/HIGH)・KPI(通過/遮断/検知/レート制限・遮断率)、
  **攻撃マップ**、リクエスト推移(分単位)、攻撃カテゴリ別(棒 + **構成比ドーナツ**)、
  検知ルール/送信元IP/攻撃箇所トップ、**IP ブロック / BAN 管理**、最近のイベント
  (行クリックでリクエスト詳細)。
- 公開範囲・ポートは `waf_config.json` の `dashboard` で設定します
  (`enabled` / `host` / `port` / `geo` / `egress`)。
- **ログは差分読み込み**: ダッシュボードは `waf.log` を毎回全部読み直さず、**前回の続きから増えた行だけ**を
  読んで累計に足します(WAFと同じプロセスで動くため、全読み込みはWAFの処理速度を落としていました)。
  合計・グラフ・マップは起動後ずっと累積され、ログが何万行・何十万行に増えても欠けません
  (旧版は末尾20万行まで)。イベントログ(最近の一覧)はメモリ上の直近2万件から表示します。
  ログを削除/切り詰めた場合は自動で最初から読み直します。

### 稼働モニター(接続先アプリ / WAF 待受)
画面上部の2つのランプで、**接続先アプリ(使用中のバックエンド。名前は登録したバックエンド名)** と **WAF 自身の待受** が生きているかを常時表示します
(3秒ごとに更新。クリックで応答時間のグラフ・最後に正常だった時刻・状態の変化履歴を表示)。

- 状態: **稼働中 / 遅い(応答が `slow_ms` 超) / 異常応答(5xx) / ダウン(応答なし) / 未確認**。
  一時的な失敗で揺れないよう、連続 `fail_threshold` 回(既定2回)失敗して初めてダウンと判定します(復旧は即時)。
- 接続先アプリ: WAF が `interval_seconds`(既定5秒)ごとに `backend_path`(既定 `/`)へ GET して確認します。
- WAF 待受: WAF が自分の待受ポートへ(TLS なら握手も含めて)接続して応答時間を測ります。確認用の接続は
  BAN/頻度制限の対象外(ただし全体の同時接続上限には従う)なので、DoS で詰まったときだけ「遅い/ダウン」になります。
- 確認のアクセスは `waf.log` にも統計にも残りません。状態が変わるとコンソールにも `[稼働モニター] ...` と出ます。
- **WAF のプロセスごと止まった場合**はダッシュボードも止まるため、画面は「応答なし」(赤)になります
  (ダッシュボードに繋がらない=WAF 側が止まっている可能性)。外部の監視ツール/別端末からは
  `https://<WAFのアドレス>:<WAFのポート(既定8080)>/health` を確認できます(WAF本体のポートです。ダッシュボードの8090ではありません)(WAF が生きていれば 200、接続先アプリがダウンなら 503、
  本文は `{"waf":"ok","backend":"up"}`)。
- **BAN・ブロック中の接続元からも `/health` だけは見えます**(`allow_when_blocked`、既定ON)。遮断対象の接続のうち
  予算内のものだけを細い通路で受け入れ、TLS握手(2秒制限)後に1リクエストだけ読んで、`/health` なら応答、
  それ以外のパスは何も返さず切ります(検査もプロキシもしません)。予算は「1接続元あたり毎秒 `blocked_ip_per_sec`(20)」
  「全体で毎秒 `blocked_total_per_sec`(100)」「同時 `blocked_max_conn`(16)」で、超えた分は従来どおり即切断です。
  ※BAN中の接続元から**フラッドが続いている間**は、中身を読むまで見分けがつかないため、予算の取り合いになり
  ほとんど入れません(攻撃が止まれば、BANが続いていても見えます)。予算を増やすとその分だけ握手の計算が増えます。
- **攻撃中でも確実に見たいとき**はダッシュボード側のアドレス `http://<WAFのアドレス>:8090/health` を使ってください
  (8080がフラッドされていても影響を受けません。応答に `waf_process` / `waf_port` / `backend` / `lag_ms` / `accept_errors` が入ります)。
  8080 の `/health` は、BAN中の接続元から**フラッドが続いている間**は見えません(上記)が、BANされていない他の端末からは見えます。
- ヘッダーの稼働ボタンは1つにまとまっており、どこを押しても詳細パネルが開きます。ナビの **「🩺 状態ログ」タブ**
  (パネル下のリンクからも開けます)では、WAFプロセス / WAF待受ポート / 接続先アプリごとの現在の状態・稼働率(24時間/7日)・
  ダウン回数、直近24時間の状態の帯グラフ、状態が変わった履歴(続いた時間つき・絞り込み・CSVダウンロード)を見られます。
- 状態の変化は `health_history.jsonl`(`health_history_file`)に保存され、WAFを再起動しても残ります。
  生存確認の時刻を `health_heartbeat.txt` に書いておき、次の起動時に「その間WAFが止まっていた」ことも履歴に追加します。
- 設定は `waf_config.json` の `health_check`(`enabled` / `interval_seconds` / `timeout_seconds` / `slow_ms` /
  `fail_threshold` / `path` / `backend_path` / `waf_probe`)。確認用アドレスを変えるときは `path`。
  ※`/health` は WAF が応答するため、接続先アプリ側に同名のパスがあっても、そこには届かなくなります。

#### イベントログの「全件読み込み」と件数の見方
- 初期表示は、同じ IP の連続した遮断(drop)ログを1行に**まとめて**(×N)表示します。
- 「全件読み込み」は、ログファイルの**全行**を、まとめずに**ログの1行=1行**で読み込みます(安全のため最大100万行、超えたら新しい方を優先)。
  表示は1000行ずつで、「さらに1000行表示」「すべて表示」で増やせます。
- 件数表示は「該当 N 行 / 読込 M 行 / 累計 X リクエスト」です。**遮断(drop)は1秒ごとにまとめて1行で記録**されるため、
  1行が複数のリクエスト(×N)を表します。このため「行数」と「累計リクエスト数」は一致しません。
- 「接続の流れ」(接続レベルのカウンター)は **🩺 状態ログ** タブに移しました。
- 攻撃インサイトの「深刻度の内訳」は、1件の攻撃を、当たったルールのうち一番重い深刻度で1回だけ数えます(合計=攻撃総数)。
  色は 危険=赤紫 / 高=橙赤 / 中=黄 / 低=黄緑 で、青系は使いません。

#### 同じPCで攻撃ツールを動かすとき(CPUの奪い合い)
- 攻撃ツールと WAF が同じPCにあると、ツールが CPU を使い切って WAF の処理が後回しになり、
  他の端末(スマホ等)が「応答時間が長すぎます」になることがあります。
- 対策として、Windows のプロセス優先度を `process_priority`(`idle` / `below_normal` / `normal`=既定 / `above_normal` / `high`)で変えられます。攻撃ツールと同じPCで「PC全体が重い」ときは `below_normal` にすると、ブラウザ等がWAFに奪われにくくなります。
  Python のスレッド切替間隔を短く(`thread_switch_interval`、既定 0.001秒)します。
- 稼働パネルの「処理の渋滞」に、**正規の接続**(稼働チェック・遮断中の通路を除く)の
  「受付→処理開始の待ち」「TLS握手の時間」「直近10秒の接続数」を出します。攻撃中にこの数字が大きい=WAF の処理待ち、
  数字が出ない/接続数が0=そもそも WAF まで届いていない(ネットワークやPC全体の渋滞)、と切り分けられます。
- 遮断中の接続元に出る表示: 予算内なら `ERR_EMPTY_RESPONSE`(握手後に何も返さず切断)、予算切れなら `ERR_CONNECTION_RESET`。

#### 大量攻撃で「ダウン(接続拒否 10061)」になる場合
- プロセスが生きていても、受付(accept)が追いつかず待受キュー(backlog)が溢れると、Windows は新規接続を
  **接続拒否(WinError 10061)** にします。これは WAF の停止ではなく「受付の渋滞」です。
- 対策として、(1) TLS はゲート通過後にワーカースレッドで握手(遮断される接続は暗号オブジェクトも作らない)、
  (2) `listen_backlog` を既定 2048 に拡大、(3) accept の失敗を数えて少し待つ(暴走防止)、を入れています。
- 追加対策: (4) 受付スレッドを `accept_threads`(既定4)本に並列化、(5) 遮断した接続は FIN ではなく RST で即破棄
  (サーバ側に TIME_WAIT が溜まらない)。実測では、遮断が毎秒約2000件で頭打ちになり、受付待ちが溢れて
  新規接続(正規ユーザーの 8080 も含む)が拒否される状態でした(受付エラー 0・スレッド遅れ小=CPU飽和ではなく受付の処理能力が上限)。
- 診断用に、稼働パネルへ「スレッド起床遅れ」と「受付エラー累計」、接続の流れパネルへ「受付エラー」を表示します。
  起床遅れが大きい=CPU/GIL飽和、受付エラーが増える=キュー溢れ/FD枯渇の兆候です。
  コンソールの `[接続/30秒]` 行にも `★受付エラー` が出ます。

### IP ブロック / BAN 管理

- **手動ブロックリスト**: IP / CIDR を入力して「ブロック追加」。常に drop されます。
  一覧の「解除」で削除。`waf_config.json` の `blocklist` に保存されます。
- **BAN履歴**: 自動BANが発動するたびに `ban_history.jsonl`(`ban_history_file`)へ保存します。WAF を再起動しても
  履歴は消えず、ダッシュボードには最新200件を表示します(単体起動のダッシュボードでもファイルから表示)。
  保存は1秒ごとにまとめて追記するので、攻撃中でもゲートの処理は遅くなりません。長くなりすぎたら起動時に末尾2000件へ整理します。
  (BAN「中」の一覧と再犯カウントは従来どおりメモリ上で、再起動でリセットされます)
- **自動BAN中**: レート制限超過で自動BANされた接続元の一覧(残り時間付き)。個別「解除」や
  「全解除」が可能。自動BANは稼働中WAFのメモリ上にあり、`waf.py` から起動した場合のみ表示されます。

### 設定をダッシュボードから変更(⚙ 設定)

右上の **「⚙ 設定」** ボタンから、WAF の設定を画面上で変更できます。**`python3 waf.py` で起動していれば、保存すると即時反映**(再起動不要)、`waf_config.json` にも保存
されます。変更できる項目:

- 動作モード(block / detect)
- 検知ルールのカテゴリ別 ON/OFF(XSS / SQLi / パストラバーサル / コマンドインジェクション)

- レート制限(ON/OFF・上限リクエスト数・ウィンドウ秒)
- ログ(PASS記録・リクエスト詳細記録・グローバルIP解決・XFF信頼・出口IP更新間隔)
- 攻撃マップ(ジオロケーション・内部IPの出口IP化)

> 待受ポート / TLS / 転送先 / ダッシュボードのポートは稼働中に変えられないため、
> 設定画面では**参照のみ**(変更は `waf_config.json` を直接編集して再起動)。
>
> **セキュリティ注意**: 設定APIに認証はありません。ダッシュボードは既定で
> `127.0.0.1`(この端末のみ)に限定しています。`dashboard.host` を `0.0.0.0` にして
> LAN公開する場合、同一ネットワークの誰でも設定変更できてしまう点に注意してください
> (信頼できる検証ネットワーク内での利用を想定)。
>
> 単体起動(`dashboard.py` を別プロセス)の場合は、保存は `waf_config.json` への書き込み
> のみで、WAF への反映には再起動が必要です。

### 単体起動(任意)

別プロセスとして単体でも起動できます(WAF側のダッシュボードを無効化したい場合など)。

```bash
python3 dashboard.py                     # http://127.0.0.1:8090
python3 dashboard.py --no-egress         # 内部IPの出口IP解決だけ無効
```

### リアルタイム攻撃マップ(SSE・完全リアルタイム)

**集計マップとは別に、発生した瞬間のリクエストだけ**を流す真のリアルタイムマップを用意しています。
WAF がログに1行書いた瞬間に、その1リクエストが Server-Sent Events(`/api/stream`)で配信され、
送信元 → 防御サーバへ1つの光点として流れ、数秒で消えます(累積なし)。

- 接続状態(ライブ接続中)、**req/s レート**、直近イベントを常時表示。
- 右上フィルタで表示する種別(通常/遮断/検知/制限)を切替。
- ネットワーク断は自動再接続します。
- **ズーム対応**: マウスホイールでズーム、ドラッグで移動、ダブルクリックで元に戻す
  (集計マップも同様)。どこから来ているか拡大して確認できます。
- **イベントログもこの SSE ストリームでリアルタイム更新**します(ポーリング待ちなし)。
  ログ表には**グローバルIPと接続元(プライベート)IPの両方**を表示します。

> 性能最適化: 以前はイベント全件(最大5000)を4秒ごとに送って再描画していたため重く
> なっていました。現在は初期120件のみ取得し、以後は SSE で差分追加・描画は間引き、
> 集計の再取得は6秒間隔に変更して軽量化しています。

### ライブ攻撃マップ(集計・直近)

全アクション(通常/遮断/検知/レート制限)の送信元を世界地図のノードとして表示し、
各ノードから**防御サーバ(出口グローバルIP)へリクエストが流れる様子をアニメ表示**します。

- ノードの色は主要アクション、大きさは件数。防御サーバは中央のパルスで表示。
- 右上の**フィルタ**(通常/遮断/検知/制限)で表示するアクション種別を切替(混雑対策)。
- 内部/ローカルからのアクセスは出口グローバルIP(=防御サーバ位置)に集約。
- ノードにカーソルを合わせると、国・IP・各アクション件数・接続元ローカルIPが出ます。

### イベントログのフィルタ / Burp風の詳細

- イベントログは**アクション/メソッド/テキスト(IP・パス・ルール)/攻撃のみ**で絞り込み可能。
- 行をクリックすると、**生リクエストと生レスポンスを左右2ペインで**(Burp Suite のように)表示。
  **受信した全ヘッダ**(User-Agent, Cookie, Sec-Fetch-*, Accept-* など DevTools と同等)・ボディ、
  応答のステータス行・全ヘッダ・ボディ、**攻撃ペイロードの一致箇所をハイライト**、各ペインに
  コピー機能、応答ステータスの色分けまで備えます。
- ログには**接続元(ローカル/プライベート)IP と グローバル(出口)IP の両方**が記録され、
  両者が異なる場合は送信元IP欄に併記されます。

### 攻撃マップ(グローバルIPのジオロケーション)

遮断した**送信元のグローバル(パブリック)IP**を国・緯度経度に解決し、世界地図へ
点灯させます。

点は2種類あります。

- **赤い点 = 外部攻撃者**: 送信元が**パブリックIP**の攻撃。IPごとに個別にジオ解決
  して点灯します。
- **オレンジの点 = 内部ネットワークからの攻撃(出口IP)**: 送信元が
  `127.0.0.1` / `192.168.x` などの**プライベート/ループバックIP**の攻撃は、
  その端末自身の**出口グローバルIP**(NAT外側の公開IP)を `ipinfo.io` 等で取得し、
  その位置に**まとめて1点**として点灯します。**このPoCのローカル攻撃はここに入る**
  ので、ローカルで試しても地図が点灯します(=およそ自分の回線/ISPの所在地)。

> 出口IPは「内部からの攻撃が外から見えるとき、どのグローバルIPに見えるか」を示す
> もので、LAN内の個々の端末を区別するものではありません。実際にインターネット経由で
> 攻撃を受けた場合は、各攻撃者のIPが赤い点で個別に表示されます。

- 出口IPの取得は `ipinfo.io/ip` →(失敗時)`api.ipify.org` → `ifconfig.me` の順。
  ジオ解決は `ip-api.com`(無料・キー不要)。結果は `data/geo_cache.json` にキャッシュ。
- 世界地図データ(`world_land.svg`)は同梱のため **CDN不要・オフラインでも描画**
  されます。

> 攻撃マップの ON/OFF は `waf_config.json` の `dashboard.geo`(ジオ解決全体)と
> `dashboard.egress`(内部IPの出口IP化)で切り替えます。単体起動時は
> `--no-geo` / `--no-egress` でも制御できます。

> ジオロケーションの精度はIPベースのため国〜都市レベルの概算です。また WAF が
> リバースプロキシやCDNの背後にある場合、送信元IPは `X-Forwarded-For` を信頼
> できる境界でのみ正確になります。

## 限界(重要)

この WAF は**署名ベースの多層防御の一層**であり、根本対策ではありません。
WAF はあくまで補助で、本質的な対策は**アプリ側の出力エスケープ / サニタイズ /
CSP(= このデモの `settings.json` のトグル)**です。署名ベースは未知・高度な
難読化を完全には防げないため、アプリ側の修正と併用してください。


## 攻撃アラート(警報バナー・EMERGENCY背景)

攻撃を検知すると、管理画面に赤×黒の警報バナーが出ます。判定はブラウザ側(ライブ配信されるイベント)で行うため、管理画面を開いていないあいだの攻撃は通知されません。

### 表示のしくみ

- **警戒 / 緊急**: 設定した深刻度(`immediate`、既定は critical)以上のルールに当たった攻撃は、**1件でもすぐ**「警戒」を表示します(例: `<script>` は critical、UNION SELECT は high)。それより軽い攻撃や、レート制限系(RATELIMIT)は、`window` 秒のあいだに `threshold` 件に達したら表示します。`critical` 件に達すると「緊急」に格上げし、勢いが落ちると「警戒」に戻ります。`immediate` は critical / high / medium / off(件数だけで判定)から選べます。
- **情報行**: 件数、攻撃元IP数(マウスを乗せるとIPごとの件数)、攻撃方法(件数の多い順に上位2つ)、攻撃元の国(多い順に上位4つ。日本語の国名)を出します。LAN内や同じPCからの接続は「日本(内部IP)」のように印を付けます。国の判定にはジオロケーションが必要で、OFFだと「不明」になります。
- **攻撃方法の表記**: 検知ルールの全カテゴリ(SQLインジェクション、パストラバーサル、コマンドインジェクション、SSRF、スキャナ等)を日本語で出します。複数のルールに当たったときは、一番重いルールのカテゴリで数えます。レート制限系は理由を日本語で出します(例: BAN発動(レート超過)、レート超過(drop)、同時接続数の超過、接続フラッド、ブロックリストIP、国ブロック)。
- **文言**: 直近の攻撃の半分より多くがレート制限系なら「大量アクセス検知」(緊急なら「DoS攻撃 発生中」)、それ以外は「不正アクセス検知」(緊急なら「大規模攻撃 発生中」)になります。
- **操作**: ページの内容は隠さず押し下げて表示します。「最小化」で細い1行になり、「閉じる」ならヘッダに「⚠ 警戒中」が残って、押すと再表示します。
- **消え方**: 攻撃が `hold` 秒間(既定2秒)来なければ、上に畳みながらフェードアウトします。出るときは上から展開し、警告文字が現れて赤い光が走ります。「警戒」→「緊急」の格上げ時は一瞬ゆれます(OSの「視差効果を減らす」設定ではアニメーションなし)。
- **表示位置**: 上部のみ / 上下の両方(既定は上部)。下部は画面下に固定され、ラベルの帯だけを表示します(詳細情報とボタンは上部バナーのみ)。上部バナーの閉じる・最小化と警戒/緊急の切り替えは下にも連動します。
- **ライト / ダーク**: ライトモードでは上下のバナーもライトテーマの配色になります。

### 六角形の背景(EMERGENCY)

- 画面の背景全体に、平常時から六角形のタイルを敷いています(枠は六角形と同じ色。ダークは黒 `#000000`、ライトは画面の背景と同じ色)。操作の邪魔にならないよう背面に表示します。
- 警戒・緊急の表示中は、六角形が順番に捲れて赤い六角形(`#e91507`、「EMERGENCY」)が現れ、その後もランダムに表裏へ回転します(緊急のときは濃く・速く)。警報が終わると赤が裏へ捲れて平常の背景に戻ります。
- 描画は canvas 1枚で、横幅を縮めて裏返すだけの軽い描き方です(影や分割なし。回転中の六角形の周りだけ描き直します)。
- 「背景の六角形」で、全体の既定・個人ごとにオン/オフできます(オフにすると点の背景になります)。

### 設定

- **全体の既定**(管理者): ⚙設定 → ログ・通知 →「攻撃アラート」。個人設定をしていないユーザーに適用されます。`waf_config.json` の `dashboard.alert`: `enabled`(既定 true)、`sound`(警報音、既定 false。ブラウザの制限で画面を一度クリックした後から鳴ります)、`threshold` 5、`window` 10、`critical` 100(0で格上げなし)、`hold` 2、`immediate`、`position`(`top` / `both`、既定 `top`)、`bg`(六角形の背景、既定 true)。
- **個人設定**(全ユーザー): 一般・アナリスト・管理者の全員が、⚙設定 の「アカウント」タブ(一般・アナリストは「アカウント・通知」)で、警報の表示・警報音・深刻度・件数・秒数・表示位置・六角形の背景を自分用に変更できます。変更は自分の画面だけに効き、`dashboard.users[].alert` に保存されます。全体の既定と**違う項目だけ**を保存するので、同じ値に戻した項目は全体の既定に従います。「全体の既定に戻す」で個人設定を消します。
- **オン/オフの優先順位**: 「攻撃アラートを表示」だけは、管理者の全体設定が優先です。全体がオフなら、個人設定にかかわらず誰の画面にも警報バナーは出ません(個人側のスイッチは押せなくなります)。全体がオンのときだけ、各ユーザーが自分用にオフにできます。ほかの項目は個人設定が優先です。
- 設定画面の「「警戒」を試す / 「緊急」を試す」ほかのテストボタンで、保存せずに見た目を確認できます(9秒で消えます)。

## 攻撃マップの全画面表示

マップのタブにある2つのマップ(リアルタイム攻撃マップ/攻撃マップ(集計))は、それぞれ右上の「⛶ 全画面」で画面いっぱいに広げられます。ブラウザの全画面(F11相当)も同時に試します。`Esc` か「✕ 全画面を終了」で戻ります。

- 全画面でもヘッダのライブ状態・req/s・フィルタ・集計期間の切替は使えます。ズーム(スクロール)・ドラッグ・ダブルクリックでのリセットも同じです。
- 攻撃アラートが出ているあいだは、バナーが最上部に表示され続け、その下にマップが収まります。大画面や壁面モニターで流しておく使い方を想定しています。

## 防御するバックエンドの指定(掲示板以外・LAN・インターネットのページ)

既定では `127.0.0.1:5000` を防御しますが、「⚙ 設定 → 防御するバックエンド」から、LAN内のサーバやインターネット上のサイトも防御対象にできます。再起動は不要で、保存するとすぐ切り替わります。

- 登録: 「名前」と「URL(例 `https://example.com` や `http://192.168.1.20:8000`)」を入力して追加します。`http` / `https` どちらも使えます。複数登録でき、「使用中にする」で切り替えます。
- 接続テスト: 各行の「接続テスト」で、名前解決(DNS)→TCP接続→TLS→HTTP応答の順に確認し、どこで失敗したかを表示します。保存前にも試せます。
- 切り替え方は2通りあります。(1) 使用中の1件に全アクセスを流す(既定)。(2) 「ホスト名で振り分ける」をONにすると、アクセスされたホスト名(例 `blog.waf.local`)を各バックエンドの「振り分けホスト名」(`match_hosts`)と照合して転送先を決めます。どれにも当てはまらなければ使用中のバックエンドへ流します。ホスト名で振り分けるには、アクセスする端末側でそのホスト名がWAFのPCのIPに向くようにします(Windowsなら `C:\Windows\System32\drivers\etc\hosts` に `192.168.x.x blog.waf.local` を追記)。
- リンクの書き換え(既定ON、`backend_rewrite_links`): 転送先がリダイレクト(Location)・Cookie(Domain属性)・ページ本文のURLに元サイトのアドレスを書くと、利用者が WAF を迂回してしまいます。そこで、それらを WAF 経由のアドレスに書き換えます(テキスト系のHTML/CSS/JS/JSONのみ。gzip/deflateは展開して処理し、画像などはそのまま通します)。リクエスト側の Origin / Referer は元サイトのアドレスに戻して渡します。
- TLS検証(`verify_tls`): https のバックエンドは、インターネット上のサイトでは証明書を検証します。LANの自己署名証明書のサーバでは、行ごとに「証明書を検証する」をOFFにして使います(既定はプライベートIPならOFF)。SNIは転送先のホスト名で送ります。
- ループ防止: バックエンドにWAF自身(待受ポート)を指定すると、転送が無限に繰り返されるため、保存時に拒否します。
- 稼働モニター: ダッシュボードの稼働表示は、使用中のバックエンドを見ます(ピルに名前が出ます)。

設定ファイルでは次のキーです(画面から保存すると自動で書かれます)。`backends` が空なら従来の `backend_host` / `backend_port`(既定 127.0.0.1:5000)を使います。

```json
{
  "backends": [
    {"id": "local", "name": "掲示板", "scheme": "http", "host": "127.0.0.1", "port": 5000},
    {"id": "intra", "name": "社内Wiki", "scheme": "https", "host": "192.168.1.20", "port": 8443,
     "verify_tls": false, "match_hosts": ["wiki.waf.local"]}
  ],
  "active_backend": "local",
  "host_routing": true,
  "backend_rewrite_links": true
}
```

### 管理画面のHTTPS
管理画面(既定 `8090` 番)は、既定でHTTPSで開きます。証明書は待受用(`tls_certfile` / `tls_keyfile`)と同じものを使い、無ければ自己署名を自動生成します(LAN の IP が変わったときも作り直します)。自己署名なので、初回はブラウザの警告で「詳細設定 → アクセス」を選びます。ログインCookieには `Secure` が付きます。

- 設定: `dashboard.tls`(既定 `true`)。別の証明書を使うときは `dashboard.tls_certfile` / `dashboard.tls_keyfile`。HTTPに戻すときは `dashboard.tls = false` か起動オプション `--no-dashboard-tls`。変更は再起動で反映されます。
- 証明書を用意できないとき(`cryptography` も `openssl` も無い等)は、警告を出してHTTPで起動します。
- 管理画面だけを単体で動かす `dashboard.py` では、`--cert 証明書.pem --key 秘密鍵.pem` を付けるとHTTPSになります。
- 以前の `http://` のアドレスでは開けなくなるので、ブックマークは `https://` に変えてください。

### ログ詳細の暗号化(個人情報の保護・キー・オフィサー)
ログに残るリクエスト・レスポンスの詳細(ヘッダ・Cookie・ボディ・クエリ)を、**組織ごとの公開鍵で暗号化して保存**します。WAFが持つのは公開鍵だけなので、運用側(管理者・アナリスト)がサーバーに入ってもログの中身は読めません。復号できるのは、**キー・オフィサー**が、**組織側の承認を受けたとき**だけです。

**役割(新しいロール「キー・オフィサー」)**

| | 管理者 | キー・オフィサー | 組織側の一般ユーザー |
|---|---|---|---|
| システム設定(ルール・ユーザー・接続先など) | 可 | **不可**(画面は 🔐暗号ログ・📨申請・ホーム等だけ) | 不可 |
| 組織ごとの鍵の登録・外す、暗号化のON/OFF | 不可(キー・オフィサーが1人もいない間だけ、初期設定として可) | 担当範囲の組織だけ可 | 不可 |
| 復号の申請 | 不可 | 可(担当範囲の接続先) | 不可 |
| 復号の承認 | 組織側に一般ユーザーも組織側アナリストもいないときだけ | 不可(自分の申請も不可) | 可(その組織の担当者。利用企業側のアナリストも承認できる。ベンダー所属のアナリストは不可) |
| 暗号文そのものの取得・復号 | **不可**(暗号文も返さない) | 承認された期間・期限内だけ可 | 不可 |
| キー・オフィサーのアカウントの変更・削除・パスワード再設定 | 鍵が登録されている間は不可(本人のみ) | 本人のみ | 不可 |

- **ベンダー側のキー・オフィサー**: 所属組織を「ベンダー」にすると、担当範囲を1つずつ選ばなくても全組織(今後増える組織も)が範囲になります。ただし復号は、これまでどおり各組織側の承認が必要です。
- **鍵は組織ごと**です(「🔐 暗号ログ」画面)。接続先の組織の鍵で暗号化し、その組織に鍵が無ければ親組織の鍵を使います。どの上位にも鍵が無い組織は、従来どおり暗号化されません。鍵ペアは画面の「鍵ペアを作成(ブラウザ内)」で作れ、秘密鍵はダウンロードされるだけでWAFには保存されません。なくすと復号できません。キー・オフィサーはユーザー管理で、担当する組織(scope)を指定して作ります。
- **復号の流れ**: ① キー・オフィサーが「復号の申請」(接続先・期間93日以内・理由)を出す → ② その組織側の一般ユーザー、または利用企業側のアナリスト(ベンダー所属のアナリストは除く)が「📨申請」で承認(1/8/24/72時間・7日の期限つき)または却下 → ③ 承認の期限内だけ、キー・オフィサーが対象期間のログを「復号して表示」できる。サーバーが暗号文を返すのは承認の条件を満たすときだけで、通常のログ画面・書き出し・API には暗号文を含めません(「暗号化されている」表示と識別子だけ)。
- **ログの探し方**: 「🔐 暗号ログ」の一覧は、イベントログと同じように、列の見出しで並べ替え(時刻・接続先・パス・IP・結果)、絞り込み(接続先・期間・メソッド・アクション・IP・パス・ステータス・承認済みだけ)、ページ送り(50/100/200件)ができます。絞り込みは暗号化していない項目だけで行うので、復号は要りません(本文の中身では絞り込めません)。
- **まとめて復号と検索**: 一覧の下の「表示中の条件で、承認済みのログをまとめて復号して一覧にする」で、承認済み(期間内・期限内)のログを最大500件、ブラウザ内で復号して一覧にします。一覧は中身(Cookie・ボディ・クエリ・パス・IP)で検索でき、一致した場所の前後が表示されます。復号した件数は、操作記録に「まとめて復号 N件」として残ります。一覧は「一覧を閉じる」・鍵を忘れる・画面を離れる・再読み込みで消えます。
- **復号結果のマスク(既定でON)**: 復号した結果は、調査に要らない情報を伏せて表示します(ブラウザ内で復号後にかけるため、サーバーには平文が渡りません)。対象は、認証情報(Cookie / Set-Cookie / Authorization などのヘッダ、`password` `token` `secret` `session` などの名前の値)と、カード番号(13〜19桁でLuhn検査に合うもの。下4桁だけ残す)・マイナンバー形式(12桁)です。検索も、マスクした内容に対して行います。調査に必要なときは「マスクを外す」で表示でき、外した操作と、かけ直した操作は操作記録に残ります(鍵を忘れる・画面を離れると、マスクONに戻ります)。番号は桁数と形式で判定するため、取りこぼしや、番号に見える別の値を伏せることがあります。
- **画面の構成(キー・オフィサー)**: 上に要約カード(暗号化ON/OFF・鍵を登録した組織数・承認待ち・いま復号できる範囲・読み込み中の秘密鍵)、その下が作業の順に並んだ4つのタブです。① 調べる(秘密鍵の読み込み → 承認済みの範囲を復号 → 検索・詳細)、② 申請、③ 鍵の管理、④ 操作記録。管理者の画面は「鍵の状態」と「操作記録」だけです。
- **鍵の登録ウィザード(③ 鍵の管理)**: ① 鍵を用意する(「鍵ペアを作成(ブラウザ内)」、または別の場所で作った公開鍵を貼り付け)→ ② 秘密鍵の保管を確認(ダウンロードした秘密鍵のファイルを選ぶと、その公開鍵で暗号化したテストデータを復号できるかを確認。別の鍵のファイルだと失敗します)→ ③ 登録して暗号化をON。②を通らないと③は押せません(別の鍵管理の仕組みで保管を確認済みのときだけ「確認せずに登録する」を選べます)。デモ用の設定 `enc_demo_keys`(既定 `true`)がONの間は、作成した鍵がその画面にだけ残り、ダウンロード・コピーを何度でもできます(画面を離れる・再読み込みで消えます)。**本番では `false` にしてください**。
- **複数の秘密鍵(鍵の入れ替え後)**: 秘密鍵は複数のファイルをまとめて読み込めます(ドラッグ&ドロップ可)。ログの鍵IDから合う鍵が自動で選ばれ、足りない鍵があるときは、その鍵IDが表示されます。
- **復号を1ボタンに**: 「鍵を読み込んだら、承認済みのログを自動で復号して一覧にする」(既定ON)。承認済みの範囲の表からは「この範囲を復号して一覧にする」で、その期間だけを復号します。
- **申請先の組織を選ぶ**: 復号の申請フォームは「申請先の組織 → 接続先」の順に選びます(ログ一覧の絞り込みも同じ)。選ぶと「申請先: ○○社 の担当者が承認します」と表示され、申請の一覧にも組織名が出ます。組織で絞ると、その配下の組織の接続先も含みます。
- **申請を楽に**: 期間のボタン(直近1時間・24時間・今日・昨日・7日)、理由のテンプレート、ログ一覧で承認が必要なログにチェックを入れて「選んだログで申請する」、申請フォームに「この期間の暗号化ログ N件」を表示。承認する側の申請画面にも、対象期間の暗号化ログの件数・組織・接続先が出ます。分まで入力した終了日時は、その分の終わり(:59)まで含めます。
- **使いやすさ**: 一覧の「この日時で申請」で、そのログの前後1時間を入れた申請フォームになります。申請の状態は「承認待ち / 承認済み(あと◯時間◯分) / 期限切れ / 却下」で色分けされます。秘密鍵のファイル(.pem)は枠にドラッグ&ドロップすると読み込まれ、残り時間が表示されます(復号・検索・詳細を開くたびに延びます)。鍵の一覧には登録日と鍵IDが出ます。
- **配色**: 暗号ログ画面の色はテーマ(ダーク/ライト)ごとに決め、文字のコントラストを4.5以上にしています(ライトは黄色・赤を濃く、ダークは赤を明るく)。
- **操作記録**: 鍵の登録/削除、ON/OFF、申請、承認/却下、復号、拒否された操作を `enc_audit.jsonl`(設定 `enc_audit_file`)に追記します。1行ごとに前の行のハッシュを含めてつなぎ(SHA-256)、書き換え・削除があると「🔐 暗号ログ」画面に警告が出ます。
- **方式**: 1件ごとにランダムなAES-256鍵で AES-256-GCM(改ざん検知つき)で暗号化し、その鍵を RSA-OAEP(SHA-256)で組織の公開鍵に包んで保存します。設定: `log_encrypt`(`enabled` / `org_keys`: 組織ID→公開鍵。従来の `public_key` は既定の鍵として読みます)。
- **画面での復号**: 秘密鍵(PEM)はブラウザの中だけで使い、サーバーには送りません。**詳細を閉じる / 無操作の時間がたつ(画面で5/15/30/60分から選択、既定30分、上限は設定 `enc_idle_max_min`)/ 読み込みから最大保持時間(設定 `enc_hold_max_min`、既定120分)/ 「鍵を忘れる」 / 画面を離れる / 再読み込み のどれかで、鍵も復号した中身も消えます**。消える1分前に警告が出て「延長する」で延ばせます(最大保持時間は超えません)。鍵の作成と復号は、画面が `https` または `localhost` のときだけ動きます(管理画面は既定でHTTPSです)。
- 暗号化するのは詳細(`req` / `resp` / `query`)だけです。時刻・接続元IP・アクション・接続先・検知ルールは、集計や地図のために平文のままです。鍵を登録する前のログ・鍵が無い組織のログは暗号化されません。外部通知(Webhook)にも詳細は含まれません。暗号化した部分は本文検索の対象になりません。
- 鍵が壊れている状態でONのままになったときは、詳細を平文で残さず捨てて記録します(`enc_error`)。
- コマンドでの復号(オフライン): `python waf_crypt.py decrypt 秘密鍵.pem ログ.jsonl`。鍵の作成は `python waf_crypt.py keygen 名前`。
- 注意: 暗号文の取得制限はサーバー側の制御で、復号の鍵はキー・オフィサーのブラウザにだけあります。最初のキー・オフィサーを作るのは管理者のため、その時点で管理者を信頼する前提になります(以後、鍵が登録されている間は管理者はキー・オフィサーを変更できません)。ONにするには `pip install cryptography` が必要です。

### 組織 → 接続先で絞り込んで見る
ホーム・マップ・トラフィック・イベントログ・IP管理・状態ログの上部に、**組織** と **接続先** のドロップダウンがあります。先に組織を選ぶと、接続先にはその組織(と配下の組織)のバックエンドだけが並びます。
組織だけ選んで接続先を「すべて」のままにすると、その組織のバックエンドをまとめた表示になります。組織が登録されていない環境では、組織の選択は出ません。
状態ログでは、防御モードと接続先アプリのカードも選んだ組織に連動します。一般ユーザーには組織の選択は出ません。
IP管理だけは設定の対象を1つに決める必要があるため、組織を選ぶと、その組織のバックエンドを1つずつ選んで設定します(「共通」は組織を選んでいないときだけ)。

### 複数のバックエンドを同時に防御する

「使用中」は1つだけですが、次の2つの方法で、複数のバックエンドを**同時に**防御できます(併用も可)。

- 専用の待受ポート(おすすめ): バックエンドの編集画面の「専用の待受ポート」に番号(例 `8081`)を入れて保存すると、WAFがそのポートも待ち受けます(再起動は不要)。そのポートに来たアクセスは、ホスト名に関係なく常にそのバックエンドへ転送します。例: 掲示板=8080(使用中)、社内Wiki=8081、外部サイト=8082。アクセス先は `https://WAFのIP:8081` のようになります(一覧に表示されます)。専用ポートも、メインと同じ HTTPS 設定・証明書・レート制限・BAN・ログを共有します。
- ホスト名で振り分け: 上の説明のとおり、1つのポートで Host ごとに分けます。DNS/hosts の設定が必要です。

決まる順番は、専用ポート → ホスト名振り分け → 使用中、です。専用ポートに指定できるのは 1〜65535 で、WAF本体やダッシュボードのポート、他のバックエンドと重複しないものです。他のプログラムが使っているポートや、転送先がWAF自身の専用ポートを指す設定は、保存時に拒否され、設定は何も変わりません。外した専用ポートはすぐ閉じます。LAN内の他の端末から使うときは、専用ポートも Windows ファイアウォールで受信を許可してください(前述)。

```json
{
  "backends": [
    {"id": "board", "name": "掲示板", "scheme": "http", "host": "127.0.0.1", "port": 5000},
    {"id": "wiki",  "name": "社内Wiki", "scheme": "https", "host": "192.168.1.20", "port": 8443,
     "verify_tls": false, "listen_port": 8081}
  ],
  "active_backend": "board"
}
```

稼働モニターは、使用中のほか、専用ポート/ホスト名振り分けで受け付けているバックエンドもすべて確認します(ヘッダの「他 N 件 稼働中」、押すと一覧)。

### ログをバックエンドごとに見る

`waf.log` の各行に、どのバックエンド宛てかを表す `backend`(id)と `backend_name`(表示名)が付きます。遮断した接続も、接続の入口(accept)で弾いたものも、専用ポートで受けたものは記録されます(ホスト名で振り分ける共有ポートでは、宛先が決まる前に弾いた接続だけ印がなく、「判定前に遮断」と表示します)。以前のログ(印なし)も、そのまま読めます。

「イベントログ」タブでは、バックエンドが2つ以上あるとき、上に**バックエンドごとの件数チップ**(合計と BLOCK / DETECT)が出ます。チップをクリックするか、選択欄で「バックエンド」を選ぶと、そのバックエンドのログだけに絞れます(アクション・メソッド・検索・期間・「攻撃のみ」とも併用できます)。表には「バックエンド」列が付き、行をクリックした詳細にも出ます。攻撃マップやトラフィックのグラフは、全バックエンドの合計です。

### イベントログの全画面表示

「イベントログ」の右上の「⛶ 全画面」で、ログが画面いっぱいに広がります(縦にも横にも表示できる行数が増えます)。`Esc` か「✕ 全画面を終了」で戻ります。全画面のまま行をクリックすると詳細が前面に出て、`Esc` を押すとまず詳細だけ閉じます。通常表示でも、ログの高さは画面の高さに合わせて広がります。

注意点・限界:

- WebSocket と HTTP/2 には対応していません(HTTP/1.1 のみ)。ボット対策(Cloudflare等)が強いサイトや、ログイン連携で元ドメイン固定のサイトは、書き換えてもうまく動かないことがあります。
- 他人のサイトを経由する用途に使わないでください。自分が管理するサイトの防御・検証用です。
- ダッシュボードを `0.0.0.0`(LANに公開)で動かしていると、LAN内の誰でもバックエンドの追加・接続テストができ、WAFのPCから内部アドレスへ接続させられる(SSRF)危険があります。ダッシュボードには認証がないため、バックエンドを変更する運用では、ダッシュボードの待受を `127.0.0.1` のみにするか、信頼できるLANでだけ使ってください。


## ログインとユーザー(ユーザーごとに見られるログが変わる)

`waf_config.json` の `dashboard.users` に、固定のユーザー名とパスワード(pbkdf2-SHA256 でハッシュ化)が入っています。起動のたびに変わることはありません。

| ユーザー名 | パスワード(初期値) | 権限 |
|---|---|---|
| `admin` | `Admin@WAF2026` | 管理者(すべてのバックエンド・全設定) |
| `user1` | `User1@WAF2026` | 一般(所属組織のバックエンドだけ。組織の割り当てが必要) |
| `user2` | `User2@WAF2026` | 一般(所属組織のバックエンドだけ。組織の割り当てが必要) |

**必ず初回ログイン後に ⚙設定 →「アカウント」タブでパスワードを変更してください。** 管理者は同じタブでユーザーの追加・削除・パスワード再設定ができます(最大20人)。

- 各バックエンドは「所属組織(`org`)」に紐づきます(登録した人では決まりません)。一般ユーザーは、所属組織(とその配下)のバックエンドの監視ログ(ホーム・マップ・トラフィック・イベントログ)だけを見られ、所属組織のバックエンドの編集・削除・稼働停止・ログ削除ができます。バックエンドの追加は管理者だけができます(一般ユーザーの画面に追加ボタンはありません)。
- 一般ユーザーには、ルール・IP管理・状態ログ・稼働モニター・防御設定は表示されません(管理者専用)。「使用中にする」も管理者だけです。
- 管理者は、設定の「組織登録編集」タブでバックエンドの所属組織を変更できます(新規追加時は編集画面でも選べます)。組織に属さないバックエンドは管理者だけが見られます。
- `dashboard.users` を空にすると従来の単一パスワード(`dashboard.password`)方式に戻ります。

## 稼働停止(バックエンドごと)

⚙設定 →「バックエンド」の「稼働停止」ボタン(またはホームの「監視中のアプリ」表)で、バックエンド単位に止められます。停止中のバックエンド宛のアクセスには **503(メンテナンス中, `Retry-After: 300`)** を返し、転送しません。設定とログは残り、状態は「稼働停止中」と表示されます。「稼働を再開」で元に戻ります(保存して適用で即時反映・再起動不要)。

## 画面ごとの機能(接続先・状態ログ・ホーム・IP管理)

### 接続先(バックエンド)の表示と色
- ヘッダの稼働ランプなどの「接続先アプリ」には、登録したバックエンドの名前が表示されます(コンソールの稼働モニターも同様)。
- ⚙設定 → バックエンド →「編集」の「表示カラー」で、接続先ごとの色を選べます。イベントログの接続先の印・件数一覧・設定の一覧に反映されます(未設定のときは自動)。
- ホームの「監視中のアプリ(接続先)」の「待ち受け」は、いまダッシュボードを開いているホスト名のURL(例: `https://192.168.200.94:8085`)で表示し、クリックで新しいタブに開きます(専用ポートがない先頭の接続先はメインの待受ポート)。転送先のURLもクリックで開けます。設定の一覧でも、待ち受け(専用ポート / メインの待受ポート / パス振り分け)のURLを開けます。
- メインの待受ポートへの、専用ポート・ホスト名の指定がないアクセスは、**バックエンド一覧の一番上**へ転送されます。
- WAF の転送・防御・稼働モニターは、誰がログインしているかに関係なく、登録済みのバックエンドすべてで常に動きます。ユーザーごとに変わるのはダッシュボードの表示(見られるバックエンド/ログ)だけです。
- バックエンドを削除すると、状態ログ(`health_history.jsonl`)からもそのバックエンドの履歴を消します。起動時にも、登録の無いバックエンドの履歴を整理します。

### 状態ログ
- 上部の「接続先」ドロップダウンで、接続先を1つ選んで、その状態・稼働率・24時間の推移・変化の履歴だけを見られます。「すべての接続先」では、接続先アプリのカードに「ダウン/異常 N件 / 全M件」と状態ごとの件数(例: 稼働中1 / ダウン1 / 稼働停止中1)が出ます。
- 登録済みのバックエンドはすべて稼働チェックし、状態の変化を `health_history.jsonl` に(バックエンドのid・名前付きで)記録します。
- 画面上部の稼働ランプは「接続先アプリ 全N件の集計 + WAF」を表示し、クリックすると状態ログタブが開きます。「稼働の詳細」(状態・応答時間・応答時間のグラフ・WAF内部の渋滞・直近の変化)は「接続先」の選択に連動し、「すべての接続先」では一覧(行クリックで絞り込み)、1件選ぶとその詳細を表示します。
- 稼働の詳細のグラフは、カーソルを合わせるとその時点の応答時間・時刻(約N秒前)を表示します(ダウンの時点は「応答なし」)。見ている間は再描画を止めて数値が動かないようにしています。
- **接続の流れ**は「接続先」に連動します。専用の待受ポートを持つ接続先(またはメインポートの転送先)は、受理・遮断・TLS握手などすべてがその接続先の分だけ出ます。ホスト名/パスで振り分ける共有ポート経由の接続先は、接続段階ではどの接続先か決まらないため、リクエスト数だけ接続先別に出ます(他の項目は「-」)。
- **一般ユーザーの状態ログ**: 自分の接続先だけ(現在の状態・稼働率(24時間/7日)・ダウン回数・24時間のタイムライン・応答時間グラフ・状態変化の履歴)と「WAF全体の稼働」(稼働中/停止/異常)の1行を表示します。WAFプロセス/待受の詳細、処理の渋滞・受付エラー、接続の流れ、エラー詳細文、CSV出力、他ユーザーの接続先は表示せず、サーバー側(`/api/health` `/api/health-log`)でも返しません。

### ホーム
- 「アクセス推移」は、グラフにカーソルを合わせるとその時点の件数(と1つ前の期間の件数)が出ます。
- 「アクセス元マップ」の円は件数にかかわらず固定サイズで、件数はカーソルを合わせると表示されます。

### イベントログ
- このタブだけ横幅の上限を外し、画面いっぱいに表示します。接続先ごとの件数(BLOCK / DETECT 含む)は、表の右側に縦並びで表示します(表示のみ。絞り込みは表の上のドロップダウン)。

### トラフィック
- 上部の「接続先」ドロップダウンで、全体または特定の接続先を選択できます。推移・攻撃種別・ルール・IP・パス・ヒートマップ・国別がその接続先だけの集計になります(`/api/stats?backend=ID`。ユーザーは自分が見られる接続先のみ)。

### IP管理
- 「設定の対象」ドロップダウンで「共通」または接続先を選択します。接続先ごとに 手動ブロック / IP許可リスト / 国ブロック / 国許可 を設定できます(`/api/security/bepolicy`、プロファイルの `ip_policy` に保存)。BAN・除外IP・同時接続制限・国不明拒否は接続段階で判定するため「共通」のみです。
- 一般ユーザーにも「IP管理」タブが出ます(自分のバックエンド宛の閲覧のみ・下記「一般ユーザーは閲覧のみ」参照)。
- 接続先ごとのIP制御の反映には WAF の再起動が必要です。

## リダイレクトの繰り返し(ERR_TOO_MANY_REDIRECTS)への対策

外部サイトを接続先にすると、サイトが「WAF が付けた X-Forwarded-Host / Proto / For」を見て自分自身へ 301 を返し、WAF がその Location を自分のアドレスに書き換えるため、ブラウザが無限にリダイレクトすることがあります。

- **転送ヘッダの個別設定**: 設定 → バックエンド → 各接続先の「編集」に「転送ヘッダ」(X-Forwarded-Host / Proto / For)のON/OFFがあります。OFFにしたヘッダは、クライアントが付けてきた分も含めて転送しません(既定は全部ON)。
- **ループ検知**: 書き換えた Location が「要求したURLそのもの」になり、同じ接続元・同じURLで15秒以内に3回続くと、WAF が 508 の説明ページを返して止めます(ログの応答詳細に `redirect_loop` を記録)。Cookie を付けて同じURLへ戻す正当なリダイレクトは1〜2回で終わるため止めません。
- **接続テストの診断**: 「接続テスト」が、WAF と同じ転送ヘッダ付きで「/」を取得し、自分自身へのリダイレクトになるかを確認します。ループになる場合は、ヘッダなし/1つずつ付けた場合も試して、引き金のヘッダ名を表示します。

## 防御モード(バックエンド別 / ルール単位の「検知のみ」)

誤検知で業務が止まったときに、防御を全体で緩めずに済むよう、防御モードを2段階で細かく切り替えられます。反映には再起動は不要です(`python waf.py` で起動している場合)。

### バックエンド別のモード切り替え

バックエンドごとに「遮断」か「検知のみ(攻撃を通してログだけ残す)」を切り替えられます。状態ログタブの「防御モード」カードで操作します。

- 一般ユーザー(提供先企業)は、自分のバックエンドだけ切り替えられます。
- 切り替えには期限(1時間 / 24時間 / 無期限)を付けられ、期限が過ぎると自動で全体設定に戻ります。
- 検知のみのバックエンドがあると、カード上部に警告(⚠ 攻撃を遮断していません)を表示します。
- 変更は履歴(誰が・いつ・どのバックエンドを)に残り、管理者の画面に表示されます。
- 管理者(提供側)は、バックエンドのモードを「ロック」できます。ロック中は一般ユーザーは変更できず、申請が必要です。

サーバー側(`/api/security/bemode`)でも権限を判定します。他人のバックエンドの変更、ロックの設定(管理者のみ)、ロック中の変更は、画面を操作しても拒否します。

### ルール単位の「検知のみ」

遮断運用のまま、特定のルールだけを「検知のみ」にできます(管理者のみ)。ルール管理タブで、各ルールの「遮断 / 検知のみ」を切り替えます。

- 1つのリクエストが「遮断ルール」と「検知のみルール」の両方に一致した場合は、遮断を優先します。検知のみルールはログに残すだけです。
- 検知のみルールだけに一致した場合は、遮断せず・自動BANもせずに転送し、DETECT として記録します(誤検知で遮断・BANしないため)。

### 保存先

`waf_config.json` に `detect_only_rules`(ルールID)と、各バックエンドの `mode_override` / `mode_until` / `mode_lock` を保存します。モード変更の履歴は `mode_history.jsonl` に残ります。設定画面でバックエンドを編集しても、これらのモード項目は書き換わりません(変更はモード切り替えの操作からのみ)。

## 追加ルール(再起動なしで追加・検証・戻せる)

新しい脆弱性への対応などで、組み込みルール(`waf_rules.py`)とは別に **`config/custom_rules.json`** にルールを足せます。WAFは3秒ごとにファイルを確認し、**検証に通ったときだけ**反映します(壊れたファイルは採用せず、今のルールのまま動き続けます。再起動は不要)。

- ルールID は `CUS-` で始めます(例 `CUS-2026-001`)。重大度 critical/high/medium/low、検査対象 all/path/query/body/header。
- **新規ルールは「検知のみ(detect)」が既定**です。ログで誤検知がないか見てから `block` に切り替えます。
- 正規表現は URL全体ではなく、**パス・各パラメータの値・本文・ヘッダー値を1つずつ**に当てます。
- 重い正規表現(入れ子の量指定子 `(a+)+`、後方参照、実測0.5秒超)は保存時に拒否します。
- 保存のたびに旧版を `custom_rules_history/` に残し、戻せます。

### ルール管理ツール(一般ユーザーが見られない別アプリ)
```
python3 src/waf_rules_tool.py --port 8099      # Windows は start_rules_tool.bat をダブルクリック
```
`127.0.0.1` だけで待ち受け(外部・別Hostヘッダー・ヘッダー無しのPOSTは拒否)。WAFと同じサーバ上でSSHトンネル等から使います。構文チェック / 試し文字列のテスト / **過去ログへの当てはめ(リプレイ)** / 保存 / 旧版へロールバックができます。リプレイは「通した通信(PASS)に何件当たるか」を出すので、遮断にしたときの誤検知の見込みが分かります。ダッシュボードの「ルール管理」にも状態と変更履歴が出ます(編集はこのツールで行います)。

## アプリごとのルール設定(管理者)

ルール管理 → 「アプリごとのルール設定」で、接続先ごとに次を設定できます(変更は `rule_history.jsonl` に記録されます)。

- ルールの **無効化** / **検知のみ**
- **除外**: ルール(または `*`)× パス(`/editor` 以下など)× 期限(1日/7日/30日/無期限)。期限が切れると自動で効かなくなります。

これらはバックエンド設定に保存され、再起動しても残ります(設定画面の保存では変わりません)。一般ユーザーの画面には出ません。

## 申請(チケット)

管理者は申請を受けて対応する側なので、申請フォームはなく、新規の申請も出せません(設定は画面で直接変更します)。

**ログの確認依頼(アナリスト → キー・オフィサー)**: アナリストが、暗号化されたログの中身の確認が必要だと判断したときは、「📨 申請」の種類で「ログの確認依頼(キー・オフィサーへ)」を選び、接続先と内容を書いて出します。担当範囲の組織を担当するキー・オフィサーだけに届き、キー・オフィサーは「暗号ログ」→「申請」で、依頼を見て、対応中・完了・却下の状態とコメントを返せます。「この依頼で復号を申請する」を押すと、接続先と理由(依頼番号つき)が入った復号の申請フォームになります。その依頼番号つきで復号を申請すると、確認依頼は自動で「対応中」になり、復号の承認・却下もコメントに残ります(「完了」にするのはキー・オフィサーです)。復号そのものは、これまでどおりお客様側の承認が必要です。

対応中の申請(問い合わせ・誤検知・ルール提案など)から直接依頼することもできます。アナリストの申請画面にある「キー・オフィサーへ依頼」に理由を書くと、元の申請の内容と番号が入った「ログの確認依頼」が作られ、元の申請にもその番号がコメントで残ります(元の申請はそのまま続けられます)。接続先のある、担当範囲の申請だけで、組織を担当するキー・オフィサーがいないと依頼できません。

一般ユーザーは「📨 申請」から **誤検知の除外申請 / 問い合わせ / 防御モードの変更依頼** を出せます。イベントログの詳細にある「これを誤検知として申請」を使うと、該当リクエストの要点(ヘッダー・本文は含めません)が添付されます。管理者は申請を確認し、**承認と同時に除外を追加**できます(期限つき・申請番号を除外に記録)。

メール通知は設定があるときだけ送ります(未設定でも申請機能は動きます)。`waf_config.json`:
```
"notify_email": {"enabled": true, "smtp_host": "smtp.example.com", "smtp_port": 587, "smtp_tls": true,
                 "username": "...", "password": "...", "from": "waf@example.com", "to": ["soc@example.com"]}
```
送信は別スレッドで、失敗してもWAFの動作には影響しません。

## 組織の木と担当範囲(提供元 / 直接契約 / 中間企業 / エンドユーザー企業)

組織を木の形で持ち、「見える範囲」は **自分の組織とその下** だけです(`waf_config.json` の `orgs`)。

```
提供元(管理者)
 ├ 直接契約企業A(SOC在中)        … 自社のWEBだけ
 └ 中間企業X(SOC)               … 他社のWEBを預かる
      ├ エンドユーザー企業B ─ 公式サイト
      └ エンドユーザー企業C ─ ECサイト
```

- 組織IDは英小文字・数字・`_`・`-`(フォルダ名に使うため)。エンドユーザー企業は中間企業の配下にだけ置けます。
- 管理者(提供元)は「ルール」タブの「組織・保存期間」で、組織の追加、バックエンドの所属の割り当て、保存期間、アナリストへのマスクの有無を設定します。
- ユーザーには所属組織(一般)または担当範囲(アナリスト。組織IDの一覧)を設定します(アカウント → ユーザー管理 → 所属・範囲)。**担当範囲が空のアナリストには何も見えません。**
- 権限の判定は `waf_org.py` の1か所に集約し、ログ・集計・IP管理・稼働・申請・設定のすべてが同じ判定を通ります(サーバ側で強制。画面のボタンを隠すだけではありません)。
- 登録者(owner)は見える範囲に影響しません。組織が未設定の古いバックエンドだけ、登録者の所属組織を移行用に使います。

### 役割ごとにできること

| | 管理者(提供元) | アナリスト(委託先・中間職) | 一般(企業の担当者) |
|---|---|---|---|
| ログ・集計の閲覧 | 全組織 | 担当範囲(機微情報は常にマスク) | 所属組織 |
| 防御モード・ルールの検知のみ/無効化/除外 | 可(ロックも可) | 担当範囲で可(**申請に紐づけて**。ロック中は不可) | 不可(申請で依頼。モードは従来どおり自分のバックエンドのみ) |
| 全ルールの除外(`*`) | 可 | 期限が必須 | 不可 |
| 追加ルールの本番反映・組織の追加・保存期間・ユーザー管理 | 可 | 不可 | 不可 |
| IP/国の制限(バックエンド別) | 可 | 担当範囲で可 | 自分のバックエンドのみ |
| 共通のBAN(全社に効く) | 可 | 不可 | 不可 |
| 申請 | 全部を確認・承認(自分では申請を出せません) | 担当範囲の申請を承認・対応、提案を出す。ログの確認をキー・オフィサーに依頼できる | 出す(誤検知・問い合わせ・モード変更依頼) |

アナリストが設定を変えるときは、担当範囲の申請の番号(`ticket`)を指定します(画面では「ルール」タブの申請番号欄、防御モードの変更時の入力)。変更履歴には、操作者・対象・申請番号が残ります。共通のBANは全社に効くため、アナリストは使えません(緊急時は、担当範囲のバックエンド別のIP制限を使います)。

### アナリストへのマスク
Cookie・認証ヘッダー・パスワード/トークン等の値は、既定で伏せて表示します。組織ごとの切り替えはなく、常に伏せます(担当範囲のログ表示・リアルタイム配信の両方に適用)。元の値が必要なときは、暗号化したログをキー・オフィサーが復号して確認します(マスクの解除は操作記録に残ります)。

## ログの保存場所・保存期間・書き出し

ログは WEB ごとの日次ファイルに記録します(`logs/` フォルダ。1つの大きな `waf.log` には書きません)。

```
logs/
 ├ _all/YYYY-MM-DD.log                提供元(管理者)用。全社のログすべて(通過を含む)
 ├ _system/YYYY-MM-DD.log             WEBに属さない記録(握手失敗・不正リクエスト等)
 ├ _unassigned/<WEB>/YYYY-MM-DD.log   組織に属さないWEBの全ログ(自動削除しない)
 ├ x/                                 中間企業X
 │   ├ _all/YYYY-MM-DD.log            Xとその配下のログすべて(SOC担当用のまとめ)
 │   └ b/                             エンドユーザー企業B
 │       ├ _all/YYYY-MM-DD.log        B社のログすべて
 │       └ b1/YYYY-MM-DD.log          WEBの全ログ(通過を含む。これが元の記録)
 └ a/ …                               直接契約企業A(同じ形)
```

- **書き込み**: ① そのWEBの日次ログ(元の記録)に書く → ② そのWEBが属する組織・上位の組織すべて・提供元の `_all` にも、同じ行を書く(1件あたり2〜4か所)。まとめがずれても、元の記録から作り直せます(`LogStore.rebuild_rollups()`。個別ログが残っている日だけ)。ログを読み書きするコードは `waf_logstore.py` に集約しています(画面や権限判定からファイルを直接開きません)。まとめのフォルダ名は `waf_logstore.ROLLUP`(既定 `_all`)です。
- **画面の表示**: 担当範囲のWEBの日次ログから読みます(絞り込みはサーバ側で強制)。「すべて」は通過(PASS)を含めて表示します。
- **WEBを別の組織へ移したとき**: 過去のログは元の組織のフォルダ(個別ログとまとめ)に残り、移した後のログは新しい組織のまとめに入ります。読み込みでは移す前の分も含めます。
- **保存期間**: 通過を含むログは既定 **30日**、攻撃の履歴は既定 **180日**。どちらも設定の「組織登録編集」タブから組織ごとに変えられ、個別ログはWEBごとの設定が優先です。個別ログは日付ごとのファイルを古い順に消します。まとめ(`_all`)は、通過の期限を過ぎたら攻撃(遮断・検知・レート制限・BAN)の行だけに絞って残し、攻撃の期限で消します。1日1回(「期限切れのログを今すぐ削除」でも)実行します。**組織に属さないWEBのログは自動削除しません**。`_system` は30日です。
- **旧い構成からの移行**: 以前の版が作った攻撃だけのまとめ(`attacks/` フォルダ)があれば、起動時に消して、`_all`(ログすべてのまとめ)を個別ログから作り直します。
- **既存の `waf.log` の変換**: 起動時に、`waf.log` が残っていれば一度だけ新しい構成へ変換し、元のファイルは `waf.log.migrated` に名前を変えます(以後 `waf.log` には書きません)。不要なら `waf.log.migrated` は削除して構いません。
- **ログの書き出し**(イベントログの「書き出し」ボタン): **管理者とアナリストだけ**です。一般ユーザーには書き出しを許しません(画面で見るだけ)。バックエンド・期間・「攻撃のみ」の絞り込みがそのまま使え、CSV または JSON Lines で出力します。
  - アナリストは担当範囲だけ(範囲外のWEBを指定すると 403)、Cookie・認証・パスワード類を常に伏せます。管理者はマスクなしです。
  - 「攻撃のみ」は、保存期間の長いまとめ(`_all`)から攻撃の行を読みます。通過を含む書き出しは、元の記録(個別ログ)から読むので、保存期間(既定30日)までです。
  - 上限は10万行です。超えたら打ち切りを知らせるので、期間を分けて書き出してください。
  - 誰が・いつ・どの範囲を・何行書き出したかは、ルール画面の変更履歴(管理者)に残ります。
- **組織まるごとの書き出し**(解約・データ返却。管理者のみ・マスクなし): 組織の「ログを書き出す」で、`log_exports/<組織>-<日時>/` に、その組織(と配下)のフォルダをそのままコピーします。
- 単体で `dashboard.py` を起動したときは、`logs/` があればそこから、なければ従来どおり `waf.log` から読みます。

## 組織の登録・編集の場所

設定画面(右上の「設定」)の「アカウント」タブの隣にある **「組織登録編集」タブ**(管理者のみ)で、組織の追加・名前/種類/親の編集・削除、バックエンドの所属組織、保存期間、マスク設定、ログの書き出し・期限切れ削除を行います。操作ごとに保存され、「保存して適用」は不要です。ルール画面には組織の設定はありません。


## ルール画面(タブ構成とバックエンド別の設定)

「ルール」は4つのタブに分かれています(バックエンド別の設定 / 検知ルール(全体) / 追加ルール / 変更履歴)。バックエンド別の設定では、組織(名前で検索可)→バックエンドの順に選ぶと、そのバックエンドだけの「有効 / 検知のみ / 使わない」をルールごとに切り替えられ、場所を絞った除外(期限つき)も追加できます。管理者は全組織、アナリストは担当範囲の組織だけが選べ、アナリストは申請番号に紐づけて変更します。他の3タブは管理者のみです。

### アナリストのルール設定の権限

- 遮断 ⇔ 検知のみ の切り替えができます。「検知のみ」への変更と除外の追加は、対応中の申請番号が必要です(遮断に戻す・再び使うは申請なしでできます)。
- 「使わない」はアナリストが直接はできません。ルール一覧の「使わない(申請)」から理由を書いて申請すると、管理者が「申請」タブの「承認してルールを使わない設定にする」で反映します。
- 「変更履歴」タブは、アナリストにも担当範囲のバックエンドの分が見えます。組織 → バックエンドのドロップダウンで絞り込めます(管理者は全体の変更も表示)。

### パス別のルール設定(検知のみ / 使わない)

バックエンドを選ぶと「バックエンド全体」と「パス別」のサブタブがあります。パス別では、パス(前方一致)ごとに、ルールを **検知のみ**(一致はログに DETECT で残り、遮断はしない)か **使わない**(一致を無視)にできます。期限を付けると切れたあと自動で元に戻ります。同じルール・パスに両方あるときは「使わない」が優先です。以前の「除外」はすべて「使わない」として引き継がれます。

- アナリスト: パス別の「検知のみ」は申請なしで追加・削除できます(全ルール `*` は期限が必須)。「使わない」は「使わない(申請して承認)」から申請し、管理者が「申請」タブで「承認して提案を反映する」と反映されます。
- 管理者: どちらも直接設定できます。誤検知の申請の承認では、「このパスでは検知のみ / 使わない」を選べます。
- 変更履歴には、モード(検知のみ / 使わない)も表示します。

応答の検査(RESP-001〜004)にも、バックエンド別の設定(使わない / 検知のみ)とパス別の設定、全体の「検知のみ」ルールが効きます。検知のみのルールは、見つけてログに残すだけで、応答の書き換え(無害化)や遮断はしません。

## 一般ユーザーは閲覧のみ(防御モード・バックエンド操作・IPブロック)

- 一般ユーザー(role=user)は、防御モードの変更、バックエンドの稼働停止・編集・削除・追加、IP/国のブロック・許可の追加と解除ができません(サーバー側も403)。画面では現在の状態だけを表示します。
- アナリスト・一般ユーザーとも、担当(所属)範囲のブロック状況(手動ブロック・許可リスト・国別制限)とBAN中の一覧は閲覧できます。BANの追加・解除・延長は管理者だけです。
- アナリストは従来どおり、担当範囲のバックエンドの防御モードとIP/国のブロック設定を変更できます。

## 申請の流れ(一般 → アナリスト → 管理者)

- エンドユーザー(中間企業の配下) → 中間企業のアナリスト → WAF提供元(管理者)
- 直接契約でSOCあり → 直接契約のアナリスト → 管理者
- **ベンダー(提供元)の組織**: `vendor` というIDの組織が最初から1つ登録されています(削除・種類の変更・親の指定はできません。表示名は変えられます)。提供元のアナリスト・キー・オフィサーはこの組織に所属させます。接続先もこの組織に持てます。古い `provider: true` のユーザーは、起動時にベンダー所属へ自動で移ります。
- 直接契約でSOCなし → **提供元アナリスト** → 管理者
- 「提供元アナリスト」は、所属組織を「ベンダー」にしたアナリスト。明示した担当範囲に加えて、担当アナリスト(提供元以外)がいない組織を自動で担当します(組織やアナリストの担当が変わると追従)。
- 一般ユーザーの申請は、その組織を担当するアナリストがいれば `stage=analyst`(一次対応)。いなければ、またはアナリスト自身の申請は `stage=admin`(管理者宛)。管理者へのメール通知は `stage=admin` のものだけです。
- アナリストは申請画面で、対応中/完了/却下、パス別の検知のみ設定ができ、自分で対応できないものは理由つきで「管理者へ依頼」できます(状態=管理者対応中。以後の状態変更は管理者)。
- 管理者の申請一覧は、アナリストが一次対応中のものを初期表示で畳みます(「すべて表示」で全件)。管理者が状態を変えると、申請者・アナリストの画面も自動更新で反映されます。
- 一次対応したアナリスト名は `handler` に記録され、一覧に「担当: ○○」と出ます。

## リロードしても同じページに戻る

いま開いているページ(設定は開いているタブも)を、URLの `#` に残します(例: `#log`、`#settings/account`)。ページをリロードしても、ホームに戻らず同じ場所が開きます。ブックマークや別タブへのURLの貼り付けでも同じページが開きます。権限のないページ(一般ユーザーの「ルール」など)や存在しない名前は、無視してホームを開きます。

## ルールのモードプリセット

- ルール管理の「バックエンド別の設定」で、接続先ごとにプリセットを選びます(5つ)。保存するのはプリセット名(`rule_preset`)と個別の上書き(`rule_detect` / `rule_block` / `rule_disabled`)だけで、ルールの中身は展開しません。画面は「標準(+3件変更)」のように表示します。
  - **標準**: critical・highは遮断、mediumは検知のみ(遮断62 / 検知のみ41)
  - **厳格**: LOGIC-006以外は遮断(102 / 1)
  - **投稿・入力型**(58 / 45) / **API型**(67 / 36) / **ファイル受付型**(65 / 38): 標準をベースに、誤検知しやすいルールを検知のみへ、そのサイトで重要なルールを遮断へ(差分は `waf_backend.PRESETS`)
- 既存の接続先は `rule_preset=""`(従来どおり全ルール遮断)のまま変わりません。画面から追加した新規の接続先は「標準」になります。
- critical の6件(XSS-001・XSS-002・XXE-001・PROTO-001・PROTO-002・RESP-001)は、どのプリセットでも遮断です。バックエンド単位で検知のみ・使わないにできるのは**管理者だけ**で、アナリスト・一般はできません(サーバー側で拒否。画面では🔒で押せません)。管理者が外した分は「標準(+N件変更)」の差分に出て、履歴にも残り、「1つ前に戻す」で戻せます。パス別の除外も管理者だけがcriticalに設定でき、アナリストが作った全ルール(`*`)の除外はcriticalには効きません。
- プリセットの変更・個別の上書きは、アナリストと管理者だけです(一般ユーザーは不可)。管理者は接続先ごとに、アナリストが選べるプリセットの範囲(`preset_allowed`。空=すべて)を決められ、範囲外はサーバー側で拒否します。
- 「詳細設定」(103ルールの一覧・パス別)は折りたたみです。プリセットを選んだあとに、ルールごとの遮断/検知のみ(基準との差分だけ保存)を変えられます。プリセットを切り替えるときは、個別の上書きを「残す / リセット」から選びます。
- 影響の見積り: 各カードに、記録されたヒットから「遮断に変わる件数 / 通るようになる件数」を自動で出します(直近30日)。「過去ログを再検査して試算」ボタンは手動で、ログのリクエスト内容(本文は先頭4KBまで・最大500件)を検査し直し、通常のリクエストが新たに遮断される件数も試算します(`waf.py` から起動した場合のみ)。
- 変更はルール履歴に変更前の状態つきで残り、「直前の変更を1つ戻す」で戻せます(戻せるのは接続先ごとの最新の1件だけ。アナリストは自分の変更だけ。戻した記録も履歴に残ります)。
